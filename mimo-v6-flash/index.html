Why Optics

Most frameworks assume a UI element has one true locator. Optics assumes an element has several plausible identities — and tries all of them before giving up.

A locator ladder, not a locator

Every keyword walks a priority-ordered chain: XPath, then visible text, then OCR, then image matching, then an opt-in AI self-heal. Cheap strategies run first — vision only costs you time when the accessibility tree can't help.

Tests are data

Elements, modules and test cases are plain CSV or YAML. Non-coders can write them, diffs stay reviewable, and there is no IDE and no programming language to learn.

Six ways to run the same keywords

CLI runner, interactive terminal, Python SDK, Robot Framework, REST API, or an MCP server. Every public method is a keyword on every surface — switch without rewriting a test.

Android, iOS, web, TV — and BLE

Selenium, Playwright, Appium, Android TV, Samsung Tizen, LG webOS. The ble driver even drives production devices over Bluetooth HID where debugging and screenshots are blocked.

The locator ladder

Every element-based keyword walks this chain until one strategy succeeds. Steps 1–4 are pluggable; step 5 is a separate recovery layer with a six-keyword allowlist, so it re-enters the ladder rather than tapping blind coordinates.

  1. 1XPathNative query through the driver's accessibility tree
  2. 2TextDirect text / CSS / class lookup through the element source
  3. 3OCRScreenshot → EasyOCR, Tesseract or Google Vision
  4. 4ImageScreenshot → template match against a reference PNG
  5. 5AI self-healOpt-in: an LLM reads the screen and recovers, bounded to five turns

Write a test as data

Optics discovers these files by their content — CSV headers or YAML top-level keys — not by their path. Repeating an element name builds a fallback list, so even the data file can heal itself.

A locator can be an XPath, text=…, css=…, a plain string, a reference PNG from input_templates/, or TEXT_ONLY:… to force a vision-based search.
